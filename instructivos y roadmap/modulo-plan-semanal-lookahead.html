Resumen ejecutivo

El residente dice qué quiere ejecutar. El ERP traduce ese plan a materiales, compras y caja.

El módulo no intenta adivinar qué rubros van a avanzar. El usuario arma el Plan Semanal / Lookahead por partida y, si hace falta, por frente o sector. Un motor determinístico convierte esas metas a cantidades físicas, explota el BOM, descuenta stock e inbound real de órdenes de compra y calcula el faltante neto y la caja adicional. El clima es un overlay opcional: evalúa factibilidad sin reescribir el objetivo ni reducir automáticamente la compra necesaria para cumplirlo.

04Metas y semántica de porcentaje

No se adivina qué significa “15%”.

CERTIFICADO
Q

QUANTITY

El usuario escribe la cantidad física que quiere ejecutar: por ejemplo 120 m².

PP

CONTRACT_PERCENTAGE_POINTS

Se calcula contra la cantidad contractual total. Ejemplo certificado: 500 m² × 10 pp = 50 m².

Capping contractual

La cantidad asignada nunca supera el remanente real: max(0, contractual − ejecutado). El mismo límite se comparte entre todos los frentes de una partida.

06Motor base determinístico

Funciona sin clima y sin LLM.

IMPLEMENTADO
ƒ

calculateWeeklyPlanRequirements

Calcula remanentes, target físico, avance ponderado, demanda de materiales, stock, inbound, faltante, valor de consumo y caja adicional. Ninguna API externa participa en esta capa.

  • Errores críticos de DB son fail-closed.
  • No convierte fallos en arrays vacíos.
  • No usa el precio unitario del rubro como costo de material.
  • Un rubro no computable nunca se presenta silenciosamente como Gs 0.

07Avance físico global

Unidades heterogéneas no se suman.

IMPLEMENTADO
%

Ponderación por valor contractual

Σ(min(ejecutado, contractual) × precio_unitario) / Σ(contractual × precio_unitario). El target usa ejecutado + plan, capado por contrato.

Semántica de UI

El KPI principal se expresa en porcentaje de avance. El valor monetario es información secundaria; nunca se etiqueta una cifra en guaraníes como “avance físico”.

08BOM y materiales

Del target físico a demanda real.

IMPLEMENTADO
B

budget_item_materials

Fuente canónica multi-material por partida. Fórmula: target × qty_per_unit × (1 + waste_pct/100).

M

material_requirement

REQUIRES_BOM, NO_MATERIAL o UNKNOWN. Ya no se infiere por palabras como “limpieza” o “flete”.

Fail-closed de BOM

REQUIRES_BOM sin receta → “MATERIALES NO CONFIGURADOS”. UNKNOWN sin receta → “REVISIÓN REQUERIDA”. Sólo NO_MATERIAL acepta BOM vacío sin advertencia.

11Capacidad histórica

Benchmark, no piloto automático.

ADVISORY
H

Comparar plan vs capacidad observada

Si hay historial relevante suficiente, muestra un rango/ritmo observado y advierte metas agresivas. Si no lo hay, dice “Sin historial suficiente para estimar capacidad”.

No existe “velocidad global de obra”

Un sector puede estar trabajando y otro detenido. La capacidad se interpreta por partida/frente relevante; nunca se extrapola un ritmo de proyecto completo a rubros inactivos.

12Weather Overlay

Opcional y separado del plan base.

LIVE
OFF

Clima apagado

No llama Open-Meteo ni LLM. El plan, materiales, stock, OC y caja siguen funcionando completos.

ON

Clima encendido

Consulta Open-Meteo con coordenadas y fechas del plan, persiste el batch y estima capacidad operativa bajo esas condiciones.

El clima nunca reescribe la intención

Objetivo 63 m² y capacidad climática 48 m² siguen siendo dos números distintos. Materiales para cumplir el plan se calculan sobre 63; consumo esperado dentro de la ventana puede mostrarse sobre 48.

13Rango exacto y cobertura parcial

Pronóstico sólo donde existe.

CERTIFICADO
7d

Semana exacta

Un plan 14/09–20/09 solicita y persiste exclusivamente 14/09–20/09. No incluye “hoy” si hoy queda fuera del plan.

16/30

Cobertura parcial

Si el proveedor sólo puede cubrir parte del horizonte, se informa X de Y días. Los faltantes no se rellenan con sol, cero lluvia ni factor 1.

15Persistencia atómica

Guardar el plan es una sola transacción.

RPC
TX

save_weekly_plan_atomic

Valida tenant/proyecto/partidas, actualiza encabezado, convierte porcentajes, comparte remanente entre frentes y sincroniza items dentro de una única transacción PostgreSQL.

Prueba certificada: plan con 3 items → payload inválido → error → rollback total → los 3 items originales permanecen intactos.

16Seguridad, RLS y grants

Tenant isolation y append-only a nivel PostgreSQL.

CERTIFICADO
A/B

JWT real entre empresas

A→A OK, A→B denegado, B→B OK, B→A denegado. Anon no puede ejecutar el RPC.

GR

Forecast append-only

authenticated sólo tiene SELECT + INSERT. No UPDATE, DELETE ni TRUNCATE. anon tiene cero privilegios.

19Qué NO hace

Límites deliberados.

DECIDIDO
×

No decide qué construir

El ERP no genera un plan operativo automático a partir de una supuesta “velocidad de obra”.

×

No predice precios de mercado

La verdad económica sigue siendo el presupuesto/costo estructurado de la empresa.

×

No compra menos por lluvia

El forecast puede bajar consumo esperado de la ventana, pero no reduce por sí solo materiales necesarios para cumplir la meta.

×

No fabrica clima

Provider caído o fecha fuera de cobertura → overlay no disponible/parcial; el plan base sigue intacto.

20Handoff

Reglas que futuros cambios no deben romper.

CERRADO
→

Invariantes

Plan del usuario ≠ capacidad estimada. Materiales del plan ≠ consumo esperado con clima. Valor consumido ≠ caja nueva. Facturado ≠ recibido físicamente. Historial meteorológico ≠ dato mutable. Sin BOM/costo confiable ≠ Gs 0.

Reabrir este módulo sólo ante un bug real o una decisión de producto nueva. BIM/APU y Certificaciones son módulos separados y ya están cerrados; el E2E global sólo debe verificar regresiones.
