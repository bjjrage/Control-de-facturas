Resumen ejecutivo

El cliente acepta la cotización; el ERP transforma esa aceptación en trabajo operativo sin volver a cargar nada.

Una proforma puede generar un link seguro de aceptación. El cliente entra sin login, revisa la versión exacta y confirma explícitamente. En la misma transacción el sistema crea un Acceptance Record inmutable y una Orden de Trabajo interna. La OT no la aprueba el cliente: sigue el circuito interno de responsable o puede ir directo a Producción por una política explícita.

Cotización → link seguro → cliente acepta → Acceptance Record inmutable → OT interna automática → aprobación interna / producción

Regla conceptual

El cliente acepta la cotización. La Orden de Trabajo es interna. Nunca existe una segunda “aceptación de OT” por parte del cliente.

02UX interna

Qué hace el usuario desde Ventas (nombres verificados en código).

IMPLEMENTADO
L

Generar link seguro

Detalle /ventas/[id] → panel “Aceptación electrónica”. Botón Generar link seguro (título Enviar a aceptación en DRAFT, Generar nuevo link (invalida el anterior) después). Campos: Vencimiento (opcional) y Email del cliente (opcional, prepara mailto:). El link congela la versión vigente y pasa la proforma a PENDING_ACCEPTANCE.

E

Preparar email

Si hay email, el panel muestra Abrir email preparado para el cliente (un mailto: con el link). Se registra EMAIL_PREPARED. Sin provider SMTP conectado, abrir el mailto: no se registra como enviado: nunca existe EMAIL_SENT.

C

Copiar link

El bloque “Link generado — se muestra una sola vez” permite copiar el secreto (en DB solo queda hash + prefijo). Pegarlo en WhatsApp/SMS/Telegram es manual. Se registra LINK_COPIED. Copiar no significa enviado ni entregado. No existe integración WhatsApp API en este flujo.

O

Abrir la OT resultante

Tras aceptar, el panel muestra “OT interna generada: {code}” con link a /ordenes-trabajo/[id] más el bloque “Registro de aceptación (inmutable)”. Acciones del link activo: Revocar link, Guardar vencimiento; historial en “Historial de links” y “Auditoría”. Rechazo/vencimiento ofrecen Reabrir como borrador.

Rutas internas reales

/ventas/[id] (panel de aceptación) · /ordenes-trabajo (lista interna “Documento interno generado automáticamente…”) · /ordenes-trabajo/[id] (detalle con “Workflow interno”, botón Aprobar para producción y selector PENDIENTE/EN_CURSO/COMPLETADA/CANCELADA + Guardar). Las políticas de routing (work_order_routing_policies) no tienen UI: se configuran en DB (backend).

03Portal del cliente

Ruta pública sin cuenta.

IMPLEMENTADO
  • Ruta pública: /cotizacion/[token].
  • No requiere login.
  • El cliente ve la versión exacta: empresa, número, fecha, validez, ítems, importes, moneda y términos.
  • El token resuelve internamente documento, tenant y versión; esos IDs no vienen controlados por el navegador.
  • El cliente ve únicamente la cotización: nunca ve ni aprueba la OT.
  • Abrir el portal solo registra visualización (VIEWED); no implica consentimiento.
  • Acción explícita requerida: el formulario “Aceptación electrónica de la cotización” pide Nombre y apellido (quien acepta) (+ documento/comentario opcionales) y exige Aceptar cotización → confirmar Confirmar aceptación (concepto: aceptar la cotización y autorizar el trabajo).
  • Rechazo explícito vía No acepto esta cotización → Confirmar que no acepto.
  • Tras aceptar se muestra “Cotización aceptada ✓”, no controles internos. El pie aclara: “Estás aceptando únicamente la cotización. La Orden de Trabajo es un documento interno y no requiere tu aprobación.”

05Orden de Trabajo

Documento interno creado desde la cotización aceptada.

IMPLEMENTADO
1

Herencia

La OT conserva referencia a la cotización/version y fotografía de sus ítems, evitando volver a cargar descripción, cantidades, precios y contexto comercial.

2

Unicidad

UNIQUE(work_orders.sales_document_id) asegura que una cotización no genere dos OTs aunque lleguen requests simultáneos.

3

Numeración

La OT recibe código interno tipo OT-2026-0002. La prueba concurrente confirmó una sola numeración para diez aceptaciones simultáneas.

4

No es evidencia del cliente

La OT es consecuencia operativa. La evidencia de consentimiento vive en sales_quotation_acceptances, no en la OT.

08Token / magic link

Capacidad pública de alta entropía, secreto fuera de DB.

IMPLEMENTADO
  • Generación en app: 256-bit con randomBytes(32), formato base64url.
  • La URL lleva el raw token.
  • DB guarda solo sha256(token) en token_hash.
  • token_prefix conserva 8 caracteres solo para soporte/correlación.
  • Lookup: hash(token recibido) → token_hash.
  • Protección contra enumeración: hash malformado o desconocido responde genérico “Enlace inválido”, sin oráculo de estado; el raw nunca viaja a la DB ni se loguea.
  • Revocación vía revoked_at, no borrado de evidencia.
  • Expiración evaluada por reloj (la más restrictiva entre link y documento).
  • Token usado por una aceptación queda protegido por FK RESTRICT.

Append-only real

Triggers BEFORE UPDATE y BEFORE DELETE rechazan cambios incluso vía service_role/postgres. Cliente, empresa, documento y token usan FKs que preservan la cadena; no hay CASCADE hacia la aceptación.

10Seguridad

Portal público estrecho, mutación solo server-side.

IMPLEMENTADO
  • Browser solo invoca server actions; no ejecuta RPCs sensibles directamente.
  • accept_quotation, reject_quotation, log_quotation_view y resolve_work_order_policy: EXECUTE solo service_role / postgres.
  • Cero grants a anon, authenticated o PUBLIC.
  • RPCs SECURITY DEFINER con SET search_path = public.
  • No hay policies anon en tablas del flujo.
  • Token, documento, tenant y versión se validan juntos; estado inválido falla cerrado.
  • Tokens completos no se registran en eventos/logs.

13Email y copiar link

Dos formas de distribuir la misma capacidad.

IMPLEMENTADO
@

Email

Hoy el repo no tiene provider de envío productivo. El módulo prepara el email/CTA vía mailto: y registra EMAIL_PREPARED, nunca un falso EMAIL_SENT. Preparar el mailto: no significa que el email se envió.

↗

Copiar link

Copia el magic link al portapapeles para pegarlo manualmente en WhatsApp, SMS, Telegram, etc. Registra LINK_COPIED; no presume teléfono, WhatsApp ni destinatario. Copiar el link no significa “enviado”. No existe integración WhatsApp API en este flujo.

Mismo flujo, distinto transporte

La aceptación ocurre siempre en el portal del ERP. Email, WhatsApp manual, SMS o cualquier otro medio solo transportan el enlace.

14Rechazo

También explícito, histórico e idempotente.

IMPLEMENTADO
  • Rechazar no crea OT ni Acceptance Record.
  • Repetir rechazo devuelve estado idempotente.
  • Una cotización ya aceptada no puede rechazarse después.
  • Para volver a negociar después de rechazo se reabre un nuevo ciclo/version/link; el histórico anterior se conserva.

18Decisiones de producto

Definitivas mientras no cambie el negocio.

IMPLEMENTADO
  • El cliente acepta la cotización, nunca la OT.
  • Magic link sin login para reducir fricción.
  • Email + copiar link; no integración directa con WhatsApp en esta fase.
  • Abrir link ≠ aceptar; el consentimiento exige CTA explícito.
  • Acceptance Record separado de eventos y OT.
  • Default conservador: aprobación interna antes de Producción.
  • OT no factura ni mueve stock.
  • No borrar evidencia: se revocan tokens, se preservan aceptaciones.

20Handoff para futuro agente

Qué no debe reinterpretarse.

INSTRUCCIONES PARA FUTUROS CAMBIOS

(1) No introducir una aprobación de OT por el cliente: el consentimiento externo termina en la cotización. (2) No convertir EMAIL_PREPARED en SENT sin confirmación de un provider. (3) Mantener token raw fuera de DB y fuera de logs. (4) No permitir que una cotización aceptada o su Acceptance Record se editen. (5) No cambiar el default a DIRECT_TO_PRODUCTION: debe ser override explícito. (6) No agregar efectos fiscales, stock o compras dentro de accept_quotation. (7) Si se agrega email real, OTP o notificaciones, deben montarse encima de este flujo sin debilitar idempotencia ni evidencia.
