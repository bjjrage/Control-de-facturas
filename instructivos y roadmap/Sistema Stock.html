INVENTARIO CANÓNICO
Resumen ejecutivo

Un solo inventario físico. Las ubicaciones explican dónde está; los movimientos explican cómo llegó; el consumo explica dónde terminó económicamente.

La cantidad física vive en inventory_balances por ubicación. El stock global no es una segunda verdad: se deriva de las ubicaciones. Las obras funcionan como depósitos físicos, la recepción genera entradas canónicas, las transferencias conservan cantidad y costo, y el consumo imputa el material a una partida presupuestaria.

1Idea central: un solo inventario canónico

ARQUITECTURA

El sistema nuevo no maneja un “stock global” y un “stock por obra” como dos cosas separadas que haya que mantener sincronizadas.

La fuente de verdad física es:

inventory_balances por ubicación física.

Cada saldo representa, conceptualmente:

empresa + producto + ubicación + moneda/costo → cantidad disponible

El stock global de la empresa se obtiene sumando las ubicaciones. Por eso no existe una segunda operación que “aumenta el stock global”: si entraron 100 unidades a una obra, el global automáticamente pasa a incluir esas 100 porque esa obra forma parte del inventario de la empresa.

Esto evita duplicaciones y descuadres.

2Las obras funcionan como depósitos / ubicaciones de inventario

ARQUITECTURA

En el modelo nuevo, una obra puede ser una ubicación física de stock.

Tipos de ubicación:

  • CENTRAL: depósito central de la empresa.
  • PROJECT: depósito/pañol de una obra.
  • AUXILIARY: ubicación auxiliar.

La tabla principal es:

inventory_locations

Una ubicación PROJECT tiene asociado obligatoriamente un project_id.

Ejemplo:

  • Empresa NIU.PACK

- Depósito Central - Obra Shopping A - Obra Edificio B - Depósito auxiliar

Todo forma parte de un mismo inventario empresarial.

3Cómo entra mercadería al stock

ARQUITECTURA

El flujo normal es:

RFQ → Orden de Compra → Recepción/Remisión → Inventario

Una OC puede venir de Administración o de una obra.

Si la compra nace desde una obra, mantiene el project_id.

Si nace desde Administración, puede ser corporativa o asignarse a una obra.

Hay una diferencia importante:

  • project_id = para qué obra/contexto económico se hizo la compra.
  • delivery_location_id = dónde físicamente entró el material.

Ejemplo:

Se compra cemento para Obra A y el proveedor entrega directamente en Obra A.

No hacemos:

entra al depósito central → sale → entra en Obra A

Eso inventaría dos movimientos.

Se registra directamente:

RECEIPT → ubicación Obra A

El stock global aumenta por agregación.

4La recepción de una OC es atómica y está protegida

ARQUITECTURA

Al confirmar una recepción, el sistema valida:

  • la OC;
  • sus líneas;
  • la empresa;
  • el producto;
  • la ubicación.

La función principal es:

inventory_confirm_receipt()

La confirmación termina generando movimientos canónicos de inventario.

También se endureció un problema importante: no se puede recibir más cantidad acumulada que la comprada simplemente haciendo varias recepciones concurrentes.

El control de recepción contra OC utiliza locking/transacción para que dos usuarios no puedan confirmar simultáneamente y saltarse el límite.

Además hay idempotencia: repetir accidentalmente una operación no debe duplicar el stock.

5Los movimientos son el libro mayor del inventario

ARQUITECTURA

Toda modificación real del inventario se representa mediante:

inventory_movements

Tipos permitidos:

  • RECEIPT: entrada por recepción.
  • TRANSFER: traslado entre ubicaciones.
  • CONSUMPTION: consumo real en obra.
  • RETURN: devolución entre ubicaciones.
  • ADJUSTMENT: corrección física controlada.

La función central para registrar movimientos es:

inventory_post_movement()

La filosofía es similar a un ledger:

  • no se pisa alegremente el historial;
  • un movimiento confirmado queda sellado;
  • si hubo un error, la corrección conceptual es mediante otro movimiento/reversión.

6Qué pasa con una transferencia

ARQUITECTURA

Ejemplo:

Obra A tiene 100 bolsas.

Se transfieren 30 a Obra B.

Resultado:

  • Obra A = 70
  • Obra B = 30
  • Global empresa = 100

El global no cambia.

Una transferencia nunca crea stock nuevo.

El movimiento contiene:

  • from_location_id = Obra A
  • to_location_id = Obra B
  • tipo TRANSFER

7El consumo es el momento económico importante

ARQUITECTURA

Cuando un material deja el pañol y realmente se utiliza, se genera:

CONSUMPTION

Un consumo tiene:

  • producto;
  • cantidad;
  • obra;
  • ubicación origen;
  • partida presupuestaria;
  • costo real.

Por eso la estructura permite asociar:

project_id + budget_item_id

El consumo es el momento en que el stock físico se transforma en:

costo real ejecutado de una partida.

Ejemplo:

Presupuesto:

Hormigón H21 → Gs. 50.000.000 previstos.

Durante la obra salen materiales del pañol imputados a esa partida.

Esos consumos forman el costo real acumulado contra el presupuesto.

Flujo conceptual:

RECEIPT → STOCK → CONSUMPTION → PARTIDA → COSTO REAL

8El stock global no mezcla costos incorrectamente

ARQUITECTURA

El inventario también guarda costo.

No solamente tenemos:

100 bolsas

También necesitamos saber:

cuánto costaron.

Por eso inventory_balances guarda información como:

  • quantity
  • total_cost
  • cost_currency
  • cost_status

Además existe:

inventory_movement_costs

Ahí se guarda el costo transportado por cada movimiento.

9Las transferencias conservan el costo

ARQUITECTURA

Si una bolsa costó Gs. 50.000 en Obra A y se transfiere a Obra B, no pasa mágicamente a otro costo.

El sistema descarga la cantidad y costo de A y transporta ese costo a B.

Esto permite que posteriormente:

CONSUMPTION

use el costo real que tenía el material.

10Manejo de moneda / FX

ARQUITECTURA

El sistema no interpreta un precio como guaraníes por defecto si no puede demostrar la moneda.

Si encuentra un costo legacy cuya moneda no puede verificarse, queda:

REVISION_REQUERIDA

en vez de inventar una conversión.

Si es una compra en moneda extranjera y falta tipo de cambio, también se conserva la evidencia pero no se finge un costo PYG confiable.

Esto evita que un stock físicamente correcto quede financieramente mal valuado.

11Inventario por ubicación, obra y global

ARQUITECTURA

Existen vistas derivadas para consultar el inventario sin crear copias.

inventory_stock_by_location

Muestra stock por ubicación.

inventory_stock_by_project

Muestra el stock asociado a obras.

inventory_stock_global

Agrupa todo el inventario computable de la empresa.

inventory_stock_global_quantity

Permite conocer cantidad global incluso cuando el costo tenga algún estado de revisión.

inventory_consumption_by_budget

Agrupa consumos por partida presupuestaria.

Así Administración puede ver:

¿cuánto cemento tengo en toda la empresa?

Y Operativo puede ver:

¿cuánto cemento tiene específicamente esta obra?

Son vistas diferentes de la misma fuente de verdad.

12Pañol: no obligamos al pañolero a usar el ERP

ARQUITECTURA

El pañolero no necesita ser usuario completo del ERP.

El depósito/pañol funciona con un:

link externo seguro

similar al enlace externo del residente o de aceptación de cotización.

Tablas relacionadas:

  • warehouse_portal_links
  • warehouse_submissions
  • warehouse_submission_evidence
  • warehouse_submission_lines

13Cómo trabaja el pañol en la práctica

ARQUITECTURA

Entradas

El pañol puede recibir mercadería y cargar:

  • foto de la remisión;
  • referencia de OC;
  • evidencia.

El sistema ayuda a conciliar contra la OC.

La confirmación humana sigue existiendo.

Salidas

No se obliga al pañolero a:

  • escanear QR cada vez;
  • entrar al ERP;
  • registrar cada bolsa en una pantalla;
  • cambiar radicalmente su forma de trabajo.

El mecanismo elegido es:

cuaderno/manual durante la semana → fotos/rendición periódica → interpretación asistida → confirmación humana

La IA puede proponer qué dice la hoja.

No se considera verdad solamente porque OCR/visión lo interpretó.

14Una rendición de pañol confirmada es inmutable

ARQUITECTURA

Una warehouse_submission confirmada no puede volver a abrirse silenciosamente.

Ni su cabecera, ni sus líneas/evidencias deben poder alterarse para cambiar el pasado.

Se agregaron triggers de base de datos para garantizarlo.

Flujo:

PROPOSED / NEEDS_REVIEW → revisión → CONFIRMED

Una vez CONFIRMED:

queda sellada.

Si hubo un error, se corrige mediante un nuevo evento/reversión, no editando la rendición histórica.

15Subidas parciales de fotos: fail closed

ARQUITECTURA

Supongamos que el pañol sube:

  • A.jpg
  • B.jpg
  • C.jpg

A y B llegan.

C falla.

El sistema usa:

  • pending_uploads
  • upload_incomplete

Cada archivo pendiente se identifica por su:

SHA-256

Si falla C, queda registrado el hash de C.

Después llega D correctamente.

D no puede limpiar C.

C solamente desaparece de pendientes cuando se vuelve a subir exitosamente el mismo contenido/hash.

Mientras exista cualquier pendiente:

upload_incomplete = true

y:

inventory_confirm_warehouse_submission()

rechaza la confirmación.

Es un fail-closed real.

16Nadie puede poner `upload_incomplete=false` manualmente

ARQUITECTURA

Un usuario authenticated no puede hacer:

UPDATE warehouse_submissions
SET upload_incomplete = false;

ni vaciar:

pending_uploads = []

Las columnas de control quedan fuera de sus privilegios directos.

La resolución del estado de uploads se hace mediante:

inventory_apply_warehouse_upload_result()

y esa función queda reservada al service_role.

Así el estado se deriva del resultado real de las cargas y no de un update arbitrario.

17Evidencias y almacenamiento

ARQUITECTURA

Existe un bucket privado:

warehouse-evidence

para fotos/documentos.

Las evidencias quedan ligadas a:

  • tenant;
  • submission;
  • ubicación/proyecto correspondiente.

También se endureció el storage para evitar que una empresa pueda leer evidencia de otra.

El aislamiento multiempresa se valida mediante:

  • RLS;
  • validaciones de tenant;
  • funciones y referencias cruzadas.

18Multiempresa / multi-tenant

ARQUITECTURA

Todo el inventario canónico lleva:

empresa_id

No basta con conocer el UUID de:

  • un producto;
  • una obra;
  • una ubicación;
  • una partida;
  • una recepción.

Las funciones validan que todas las piezas pertenezcan a la misma empresa.

Ejemplos:

  • una ubicación de Empresa B no puede usarse en un movimiento de Empresa A;
  • una partida de una obra no puede utilizarse para imputar consumo de otra obra;
  • una OC de otro tenant no puede utilizarse para una recepción.

19Qué ocurrió con el sistema legacy

ARQUITECTURA

Producción tenía una historia distinta al modelo nuevo.

Originalmente había existido:

  • depositos
  • stock_por_deposito

Pero esas tablas ya no estaban realmente presentes en producción.

El sistema legacy vigente tenía principalmente:

  • stock_movimientos
  • stock_por_proyecto
  • productos.stock_actual

Durante el pre-flight se descubrió que la migración nueva todavía esperaba depositos/stock_por_deposito.

Eso hubiera hecho fallar producción.

20El hotfix final

ARQUITECTURA

Como el inventario canónico todavía no había sido instalado en producción, se corrigió la baseline antes de ejecutarla.

Se quitaron:

  • el backfill desde depositos;
  • el backfill desde stock_por_deposito;
  • la escritura futura a stock_por_deposito.

No se inventó un mapeo desde el sistema viejo porque el stock legacy encontrado tenía apariencia de fixture/demo y, además, no contenía información suficiente para reconstruir correctamente una ubicación física.

El inventario canónico arrancó:

vacío.

Se mantuvo una compatibilidad:

productos.stock_actual

se actualiza como proyección del inventario canónico.

21Qué NO hacemos con el legacy

ARQUITECTURA

No hacemos:

  • movimientos artificiales para justificar saldos viejos;
  • depósitos inventados;
  • conversión automática de stock_por_proyecto en ubicaciones físicas;
  • copia de fixtures al inventario nuevo;
  • mantenimiento de stock_por_deposito.

El viejo /stock queda como superficie legacy/compatibilidad, no como la fuente canónica nueva.

22Flujo completo real

ARQUITECTURA

Compra

RFQ → OC → proveedor entrega → recepción/remisión → RECEIPT → inventory_balances

Movimiento interno

Inventario Obra A → TRANSFER → Inventario Obra B

Uso

Inventario Obra B → CONSUMPTION → partida presupuestaria → costo real de obra

Pañol

Cuaderno/fotos → rendición → IA/OCR propone líneas → humano revisa → warehouse_submission → confirmación → movimientos de inventario → saldos actualizados

23Ejemplo concreto

ARQUITECTURA

Se compran:

1.000 bolsas de cemento

para Obra A.

El proveedor entrega directamente en Obra A.

Resultado:

  • Obra A = 1.000
  • Global = 1.000

Después se transfieren 200 a Obra B:

  • Obra A = 800
  • Obra B = 200
  • Global = 1.000

En Obra A se consumen 150 para la partida “Fundaciones”:

  • Obra A = 650
  • Obra B = 200
  • Global = 850

Además:

Partida Fundaciones → 150 bolsas consumidas + costo real transportado

24Qué significa realmente “stock” ahora

ARQUITECTURA

Ya no es simplemente:

productos.stock_actual = 850

El sistema sabe potencialmente:

  • hay 850 unidades globales;
  • 650 están en Obra A;
  • 200 están en Obra B;
  • 150 fueron consumidas en Fundaciones;
  • esas 150 tuvieron determinado costo real;
  • las restantes mantienen el costo con el que ingresaron;
  • sabemos de qué recepción/movimiento provinieron;
  • sabemos qué empresa y obra corresponden.

Ese salto convierte el antiguo “stock” en:

inventario operativo + contabilidad de materiales de obra

✓Estado final

ESTADO FINAL

A nivel conceptual, el sistema queda así:

OC → recepción → ubicación física → stock canónico → transferencia → consumo → partida → costo real

con:

  • pañol externo;
  • evidencias;
  • controles de concurrencia;
  • idempotencia;
  • multi-tenant;
  • costos/FX fail-closed;
  • inmutabilidad de eventos confirmados.

La regla que resume la arquitectura es:

La cantidad física vive en inventory_balances; los movimientos explican cómo llegó ahí; el consumo explica dónde terminó económicamente.
