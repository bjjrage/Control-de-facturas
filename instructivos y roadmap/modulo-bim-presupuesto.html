Resumen ejecutivo

Cruzar cantidades de obra contra el presupuesto sin cargarlo a mano, con o sin modelo 3D.

BIM Viewer parsea un IFC, renderiza el modelo 3D y agrupa elementos por tipo + material. Pipeline semántica usa DeepSeek para sugerir qué rubro del presupuesto corresponde a cada grupo o ítem, con una capa de integridad técnica determinística previa. Cómputo Métrico extiende la misma pipeline a Excel y PDF para proyectos sin modelo IFC: el costeador sube su planilla y el sistema sugiere los rubros automáticamente.

01Resumen ejecutivo

Qué hace cada pieza y qué problema resuelve.

IMPLEMENTADO
A

BIM Viewer — el visor 3D

Renderiza un archivo IFC en WebGL (web-ifc + Three.js). Permite navegar el modelo en 3D, seleccionar elementos individuales y ver sus propiedades. Calcula automáticamente bounding box y centra la cámara.

B

Pipeline semántica — el matcher

Agrupa elementos IFC por tipo + material → filtra candidatos de presupuesto técnicamente compatibles → corre integridad determinística → pasa a DeepSeek que sugiere el rubro con mayor confianza. Sin modelo IFC el input son filas de Excel/PDF.

C

Revisión humana — el cockpit

Cards de revisión con badges de estado (SUGGESTED · REVIEW · REVIEW_REQUIRED · NO_MATCH). El costeador confirma, cambia rubro o deja sin asignar. Solo las confirmadas cuentan para el export.

D

Cómputo Métrico — sin IFC

Para proyectos sin modelo BIM. El costeador sube su planilla Excel o PDF. El sistema extrae filas (descripción / cantidad / unidad) y las pasa por la misma pipeline semántica. El PDF tiene un gate de confianza de 3 capas antes de correr el matching.

Idea central

El costeador ya tiene su planilla de presupuesto y recibe el cómputo métrico (desde BIM o desde Excel/PDF). El módulo cruza ambos automáticamente y solo le pide al humano que confirme las sugerencias dudosas — no que las cargue a mano.

Separación cliente/servidor

El parser IFC y el visor 3D corren SOLO en el browser (.client.ts) — no pueden importarse en server actions. El PDF extractor y el matcher DeepSeek corren SOLO server-side: necesitan la API key que nunca sale al cliente.

03Visor 3D

web-ifc + Three.js en el browser.

IMPLEMENTADO
W

web-ifc v0.0.68 — WASM

El parser IFC usa un módulo WebAssembly. Requiere SetWasmPath("/wasm/", true) — el segundo argumento true es obligatorio para que la ruta sea absoluta. Sin él, web-ifc prepende la ruta del bundle JS y falla.

P

Proxy middleware — WASM público

proxy.ts (middleware Next.js) protege todas las rutas excepto las declaradas públicas. Se agregó path.endsWith(".wasm") a la lista de rutas públicas para que el browser pueda descargar el WASM sin ser redirigido a login.

F

fitAll / fitSelection

modelRoot.updateMatrixWorld(true) debe llamarse ANTES de Box3.expandByObject(). Sin esa llamada, Three.js calcula el bounding box con matrices identidad (pre-primer-render) y la cámara queda mirando al origen, con el modelo fuera de vista.

I

Inspector de propiedades

Al clickear un elemento en el visor, el inspector muestra expressId, tipo IFC, nombre, storey y property sets. Los property sets solo existen si el arquitecto habilitó la opción de exportación en Revit/ArchiCAD — no todos los IFC los tienen.

IFC sin geometría — comportamiento esperado

Un IFC puede tener elementos sin geometría (IFCEXTRUDEDAREASOLID = 0). El visor carga correctamente pero muestra canvas en negro. No es un bug: algunos IFC se construyen solo para pruebas semánticas. El fixture aurora-mixed-elements.ifc es de ese tipo; IfcOpenHouse.ifc tiene geometría real (43 meshes).

04Parser IFC

Extracción de elementos y propiedades.

IMPLEMENTADO
E

Elementos — ifc-parser.client.ts

Itera todos los tipos IFC relevantes (IFCWALL, IFCSLAB, IFCCOLUMN, …). Por cada elemento extrae expressId, name, type, storey, material, property sets y quantity sets. El resultado es un array de BimElement.

Q

Quantity Sets

Cuando el IFC los tiene (IfcQuantityArea, IfcQuantityLength, …) se leen directamente. Si no existen, la cantidad queda null. El sistema nunca inventa cantidades — o las lee del IFC o las deja vacías.

Lazy import de web-ifc

El módulo web-ifc solo se importa dentro de funciones, nunca en el top-level del archivo. Next.js haría SSR del bundle de cliente si el import fuera top-level y el WASM no existe en el servidor.

05Agrupador BIM

Muchos elementos idénticos → un grupo → una línea de presupuesto.

IMPLEMENTADO
G

Clave de grupo

groupKey = ifc_type + "|" + normalize(material) + "|" + storey. Elementos con la misma clave se consolidan en un único BimElementGroup. La cantidad del grupo es la suma de las cantidades individuales.

R

Por qué agrupar

Un modelo real tiene 200 columnas de hormigón H-30 distintas (cada una con su expressId). En el presupuesto hay una sola línea "Hormigón armado H-30 columnas". El agrupador colapsa las 200 en un grupo; el matcher trabaja sobre el grupo, no sobre cada columna individual.

Cómputo Métrico no necesita agrupar

Una planilla Excel o PDF ya viene como una fila = un ítem de presupuesto. El agrupador no se usa en ese camino. La función computoItemToBimElement convierte cada fila directamente al shape de BimElement para reutilizar la misma pipeline.

06Pipeline semántica

Retrieval determinístico → integridad → DeepSeek.

IMPLEMENTADO
Budget ItemsTodos los rubros hoja del proyecto (con precio unitario).
→
buildCandidatePoolFiltro determinístico: unidad compatible + specs técnicas compatibles (espesor/resistencia). Máx. 12 candidatos.
→
checkTechnicalIntegrity¿El elemento tiene contradicciones internas? Si sí → fuerza REVIEW_REQUIRED.
→
DeepSeekBatchSemanticMatcherPrompt estructurado + JSON mode. Devuelve: MATCH + candidateId + score + reason, o REVIEW, o NO_MATCH.
→
Status assignmentSUGGESTED · REVIEW · REVIEW_REQUIRED · NO_MATCH según resultado y flags de integridad.
Batch de 8

El matcher agrupa hasta 8 elementos por llamada a DeepSeek para reducir latencia. Cada llamada devuelve un Map<elementId, MatchResult>. Si la llamada falla a mitad, se reportan los ítems procesados antes del error y el error es transparente — nunca hay un fallback silencioso.

07Integridad técnica

Capa determinística previa al matching — detecta contradicciones en el input.

IMPLEMENTADO
1

CONFLICTING_MATERIAL

El nombre del elemento clasifica en una familia de material (ej. "cerámica") pero el campo material clasifica en otra (ej. "hormigón"). Solo se activa cuando AMBAS fuentes clasifican con confianza y difieren.

2

CONFLICTING_THICKNESS

El espesor extraído del texto (nombre/material/tipo) difiere en más de 15mm del espesor declarado en properties. Ej.: nombre dice "150mm" pero properties.thickness = 100.

3

CONFLICTING_STRENGTH

El grado/resistencia extraído del texto (H-30, CA-50) difiere del declarado en properties. Mismo patrón que espesor pero para resistencia de hormigón y acero.

4

AMBIGUOUS_RANGE

El texto contiene un rango explícito ("entre 15 y 20 cm") y existen rubros de presupuesto con espesores DISTINTOS dentro de ese rango. DeepSeek podría elegir cualquiera correctamente — se fuerza revisión humana.

Comportamiento cuando es vicious

La integridad NO descarta candidatos ni bloquea DeepSeek. DeepSeek sigue corriendo y sigue proponiendo. Lo que cambia es que el status final se fuerza a REVIEW_REQUIRED independientemente de la confianza del matcher. El reason del matcher queda adjunto como información para el humano.

08DeepSeek Batch Matcher

Matching semántico vía LLM — deepseek-v4-flash.

IMPLEMENTADO
M

Modelo y modo

deepseek-v4-flash, temperature: 0, response_format: { type: "json_object" }. JSON mode garantiza output parseable. Temperature 0 para reproducibilidad.

P

Prompt estructurado

El sistema explica el dominio (construcción paraguaya, rubros de presupuesto). El usuario entrega el elemento + sus candidatos pre-filtrados. El modelo devuelve { decision, candidateId, confidence, reason } por elemento.

K
DEEPSEEK_API_KEY

Variable de entorno requerida en Vercel. Nunca se loguea. Si no está, el matcher lanza inmediatamente — sin fallback silencioso. Nombre exacto: DEEPSEEK_API_KEY (no DEEPSEEK).

S

Safety taxonomy

EXACT_CORRECT · SAFE_ABSTENTION · REVIEW_REQUIRED · UNSAFE_MATCH · WRONG_MATCH. Usada en los benchmarks adversariales para medir la calidad del matcher, no en producción directamente.

09Estados de match

El ciclo de vida de cada ítem desde sugerencia hasta confirmación.

IMPLEMENTADO
SUGGESTEDDeepSeek encontró un match con confianza alta y sin flags de integridad. Listo para confirmar con un click.
→
REVIEWDeepSeek no pudo decidir (ambigüedad semántica). Requiere que el humano elija manualmente.
→
REVIEW_REQUIREDIntegridad técnica detectó contradicción. Aunque DeepSeek propone, el humano DEBE revisar antes de confirmar.
→
NO_MATCHNingún candidato plausible. El humano puede buscar manualmente o dejar sin asignar.
✓

CONFIRMED

Decisión humana final. Se escribe en DB con confirmed_by y confirmed_at. Solo los CONFIRMED aparecen en el export a Excel. Un ítem solo puede tener un CONFIRMED activo (unique index).

✗

REJECTED

El humano decidió que el ítem no tiene rubro equivalente. Se registra con method: MANUAL. No aparece en el export. El costeador puede reactivarlo manualmente si cambia de opinión.

10Revisión humana

El cockpit de confirmación — cards por ítem.

IMPLEMENTADO
C

Cards de revisión

Una card por grupo BIM o ítem de cómputo. Muestra: badge de estado, descripción del ítem, cantidad + unidad, rubro sugerido (si hay), score de confianza y reason del matcher.

A

Acciones disponibles

Confirmar: acepta la sugerencia actual (o el rubro elegido manualmente). Cambiar rubro: abre selector de presupuesto para asignar manualmente. Dejar sin asignar: marca como REJECTED.

E

Export a Excel

Botón por import de cómputo. Genera una hoja con: código de rubro, descripción, cantidad confirmada, unidad, precio unitario y total. Usa XLSX.writeFile (misma librería que el import de presupuesto). Solo items CONFIRMED.

R

Retry tras BAJA_CONFIANZA

Un PDF marcado como BAJA_CONFIANZA (gate activado) no corre el matching automáticamente. El humano puede revisar las filas extraídas, editar las sospechosas y luego pedir el matching manualmente vía retryComputoMatching.

¿Por qué no hay gate de confianza para Excel?

El Excel ya viene estructurado — el usuario mismo mapeó las columnas. La ambigüedad de "¿es una tabla legible?" no existe. El gate de 3 capas solo aplica a PDF, donde la extracción es no determinística.

13Gate de confianza — PDF

3 capas determinísticas antes de gastar tokens de IA en matching.

IMPLEMENTADO
1

Señal estructural — gratis

pdf-parse extrae el texto. Si el texto tiene menos de 40 caracteres → el PDF es probablemente un escaneo sin capa de texto → vicious = true inmediatamente, sin llamar a DeepSeek.

2

Confianza auto-reportada por DeepSeek

El prompt pide un flag tabla_clara: boolean además de las filas. Si DeepSeek mismo dice que no encontró una tabla clara → vicious = true. La IA admite cuando no puede leer.

3

Sanidad determinística por fila

Por cada fila extraída: descripción vacía → issue. Cantidad no finita o ≤ 0 → issue. Unidad no reconocida por normalizeUnit → issue. Si más del 33% de filas tienen issues o la confianza promedio < 0.5 → vicious = true.

!

Cualquiera de las 3 alcanza

No hace falta que fallen las 3 capas. Una sola captura basta para marcar BAJA_CONFIANZA. Preferimos falsos positivos (pedir revisión de más) a falsos negativos silenciosos.

pdf-parse — import perezoso obligatorio

pdf-parse tiene una dependencia nativa (pdfjs-dist) que rompe en Vercel si se importa en el top-level del archivo. Se importa dentro de la función con await import("pdf-parse"). Mismo patrón que lib/invoice-extraction.ts.

BIM y Cómputo tienen sus propias tablas. bim_elements tiene ifc_guid NOT NULL — meter una fila de Excel ahí rompería el constraint. La separación también evita que un bug en Cómputo pueda corromper datos BIM.

16Seguridad

RLS, storage y secretos.

IMPLEMENTADO
  • RLS por empresa: toda tabla filtra por current_empresa_id() — una empresa nunca puede leer datos de otra aunque conozca el UUID.
  • is_internal_role(): escritura restringida a roles administracion / admin. Rol comercial solo lectura.
  • requirePlan("caterpillar", [...]): todas las server actions verifican plan + rol antes de tocar DB.
  • DEEPSEEK_API_KEY: nunca se loguea, nunca sale al cliente. Si falta, las actions lanzan con mensaje claro — sin fallback silencioso que enmascare el error.
  • Storage privado: buckets bim-models y computo-imports no son públicos. Los archivos se descargan server-side vía service role.
  • storagePath: incluye project_id + UUID. Path collision imposible entre proyectos.

18Decisiones de producto

Definitivas, no reabrir sin motivo.

IMPLEMENTADO
  • Tablas separadas para BIM y Cómputo: no mezclar bim_elements con filas de Excel/PDF — el constraint ifc_guid NOT NULL lo impediría y la semántica es distinta.
  • DeepSeek, no OpenAI: todo el módulo usa un solo proveedor de IA. No agregar un segundo proveedor para el extractor PDF.
  • Gate de confianza solo en PDF: Excel ya viene estructurado por el usuario — el gate no aplica.
  • Temperature 0 en todos los prompts: reproducibilidad sobre creatividad. El matcher no debe inventar.
  • El visor 3D es informativo, no operativo: no se puede confirmar un match desde el visor. Matching y confirmación van en la sección de cards debajo.
  • Cantidad del grupo = suma, no promedio: en presupuesto lo que importa es la cantidad total de material a comprar, no la cantidad promedio por elemento.
  • REVIEW_REQUIRED no bloquea DeepSeek: el matcher siempre propone. La integridad solo cambia el status final — el reason del matcher queda visible para ayudar al humano.
  • Export solo CONFIRMED: nada ambiguo sale al Excel final. El costeador exporta cuando está listo, no antes.

20Handoff para futuro agente

Instrucciones de ingesta al manual maestro.

INSTRUCCIONES PARA EL AGENTE QUE INTEGRE EL MANUAL FINAL

Este HTML es un módulo independiente ("bloque de conocimiento"). Al integrarlo al capítulo "BIM / Cómputo Métrico" del manual maestro: (1) mantener la separación BIM vs Cómputo — son dos caminos de entrada a la misma pipeline, no el mismo feature; (2) no confundir "visor 3D" con "matching" — el visor es informativo, el matching es el valor; (3) preservar los 6 estados tal cual, especialmente la diferencia entre REVIEW (ambigüedad semántica) y REVIEW_REQUIRED (contradicción técnica); (4) no presentar las funcionalidades PENDIENTE como existentes; (5) recordar que DEEPSEEK_API_KEY debe estar en Vercel con ese nombre exacto y nunca puede loguearse; (6) el flag absolute=true en SetWasmPath es obligatorio — sin él el WASM no carga.
